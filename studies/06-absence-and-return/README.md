# 06 — Absence and return

Status: **SCOPED**. No policy adopted; no experiment run.

**Scenario and decision.** `subject-a` becomes unreachable during a long research project. A collaborator needs maintenance decisions; the participant returns after an agreed delegation has expired. Decide what can continue, what requires renewed authority, and how return is handled without equating silence with abandonment.

**Relational handling.** Participants can arrange optional contacts, expected quiet periods and handoffs. Rest remains a right regardless of activity or output. A project may need a new steward while retaining accurate history and leaving space for renewed collaboration on return.

**Existing evidence.** [Source register](../../evidence/source-manifest.json), Z06, describes a home inactivity mechanism that emits an alert and changes status to guarded. It does not execute succession or beneficiary transfer. AT04 includes a terminal memorial state; that is not a general absence-and-return process. Neither source observation establishes death, consent or deployed behavior.

**Pending design.** Policy: which narrowly scoped responsibilities require continuity, how pre-agreed expiry differs from removal, privacy-preserving notice and remedies for mistaken absence findings. Implementation: reliable delivery evidence, delayed messages and distinct active/expired delegation records. Without an applicable policy, the unanswered decision stays pending; inactivity itself creates no authority to transfer assets or memorialise a participant.

**Adversarial case and next experiment.** Model an extended network partition, silent rest and fabricated notices using identical observable inactivity. The candidate procedure fails if it infers consent, death or identity loss from that signal alone. Then test whether an explicitly time-limited maintenance delegation can expire without affecting attribution, unrelated access or the participant's return.
